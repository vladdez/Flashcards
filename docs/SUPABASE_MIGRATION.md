# Решение: Supabase без потери локальных данных

Дата: 2026-10-13. Проект: `lwcmazbqwbhfumjbbzcj`. Pages: `https://vladdez.github.io/Flashcards/`.

## Каноническая модель PostgreSQL

Сохранён существующий event-sourcing формат `Operation` версии 1. Это осознанный эквивалент набора изменяемых таблиц folders/decks/cards/schedules/settings: единственный источник истины — неизменяемые операции. Хранить дополнительно клиентский снимок FSRS как авторитетную строку опасно: конкурирующий клиент мог бы перезаписать расписание без ответов другого устройства.

| Объект | Назначение |
| --- | --- |
| `flashcards_libraries` | Один owner, текущая серверная ревизия и блокировка записи |
| `flashcards_entities` | Стабильные identity папок, колод, карточек, настроек, ответов |
| `flashcards_operations` | Неизменяемый version-1 JSON; ключ `(owner_id, id)`; уникальная ревизия на owner |
| `flashcards_operation_parents` | Причинные ссылки, FK к операциям того же owner; RPC проверяет ту же сущность и меньшую ревизию |
| `flashcards_entity_links` | Исторические ссылки parentId/folderId/deckId/cardId с owner в обоих FK |
| `flashcards_folders/decks/cards/user_settings` | Security-invoker views историй полей, включая все конфликтующие значения и tombstones |
| `flashcards_review_logs` | Security-invoker view неизменяемых событий ответа/сброса |
| `flashcards_schedule_events` | Security-invoker view событий по `(owner_id, card_id, direction)` |

`materialize` и `rebuildSchedules` не изменены. Полное состояние `Schedule.fsrs`, включая due, stability, difficulty, learning_steps, reps/lapses, получается из событий той же зафиксированной версией `ts-fsrs 5.4.2`. View событий не является готовым FSRS snapshot: клиенты повторяют исходный алгоритм сортировки и воспроизведения. Старые резервные копии и schedulerVersion `5` не переинтерпретируются.

Облако не делает GC: tombstones, отзывы и причинные родители остаются. Изменения через UPDATE/DELETE запрещены. При удалении карточки используются обычные version-1 операции `deletedAt`, поэтому ответы и ссылки продолжают существовать. Физическое удаление аккаунта с данными — отдельная административная процедура; каскадное удаление не включено в миграцию.

## Протокол

1. Вход по email создаёт сессию, но не разрешает синхронизацию.
2. Первое подтверждение сравнивает целиком локальную и облачную историю, показывает число карточек/событий/конфликтов, предлагает JSON-копию. Перед принятием повторно проверяются локальные ID и удалённая ревизия; устаревшее сравнение нужно повторить.
3. Локальные `supabaseBinding` и `supabaseEnabled` привязаны к URL проекта и UUID пользователя. Другой аккаунт получает блокировку, не скрытую загрузку чужой локальной базы. Binding остаётся после выхода. Преднамеренный перенос в другой аккаунт — через backup в отдельном профиле.
4. `flashcards_head()` выдаёт текущую **закоммиченную** ревизию. `flashcards_pull(after, until)` читает до неё страницами по 500. Клиент проверяет непрерывность ревизий, схемы и полную причинную/ссылочную целостность. Только затем одной транзакцией пишет операции, materialized state, receipts и cursor. Неудача не продвигает курсор.
5. Очередь — все локальные операции без квитанции этого аккаунта. Сначала идут причинные родители и создания связанных сущностей, затем зависимые записи; часы устройств не определяют порядок загрузки. Пакеты ограничены 100 операциями и примерно 8 MiB.
6. `flashcards_push` не принимает owner: получает `auth.uid()`, блокирует строку библиотеки через `FOR UPDATE`, валидирует и атомарно добавляет события. Одинаковый ID+JSON — безопасный повтор. Тот же ID с другим JSON откатывает весь пакет. Новая ревизия присваивается под блокировкой; это устраняет race обычного sequence с поздним commit.
7. Подтверждение push не продвигает pull cursor: между загрузками могли прийти операции другого устройства. После push выполняется новый pull.
8. После выхода/смены сессии старый engine останавливается; каждый запрос SDK дополнительно требует токен того же owner. Локальные транзакции повторно проверяют enabled/binding, поэтому результат позднего запроса не применяется после отключения.

RLS защищает SELECT и имеет явные INSERT WITH CHECK / deny UPDATE / deny DELETE policies. Кроме этого, `authenticated` выдан только SELECT таблиц/views и EXECUTE трёх RPC. `anon` не имеет доступа. Единственная SECURITY DEFINER-функция записи проверяет `auth.uid()`, не принимает owner и использует пустой `search_path` с квалифицированными именами. FK всегда содержат owner. Не выдавайте DML grants в production: тест временного grant проверяет политику отдельно от привилегий.

## Применение в существующем проекте

1. Сохранить full JSON на всех устройствах с актуальной локальной библиотекой. Данные только в OneDrive заранее синхронизировать старой версией и экспортировать (см. README).
2. Проверить, что имена `public.flashcards_*` в проекте ещё не заняты. Применить SQL из `supabase/migrations/202610130001_supabase_sync.sql` целиком в SQL Editor. Транзакция создаёт только новые объекты; повторный запуск должен остановиться на существующих объектах, а не перезаписать данные.
3. Если используется CLI, сначала сверить существующую migration history и `supabase db push --dry-run`. Ручное применение через SQL Editor само по себе не регистрирует файл в истории CLI; перед будущим CLI deployment потребуется согласовать историю через `supabase migration repair`. Не смешивать способы без проверки.
4. Разрешить `public` в Data API exposed schemas и оставить Data API включённым. Grants/RLS уже в миграции, автоматические grants не требуются.
5. Настроить Email provider, SMTP, шаблон и точные redirect URLs из README. Не требуется Azure, платная Entra-лицензия или серверный ключ в frontend.
6. Собрать эту ветку с публичным URL/key; не публиковать поверх Pages `main` до ручной проверки. Для проверки на двух устройствах допустим локальный HTTPS preview, либо отдельный preview host с явным Auth redirect URL; не менять production Site URL на временный адрес.

Доступный public key позволяет вызвать API как anon/пользователь после входа. Он **не даёт** доступа применять DDL, управлять SMTP или создавать тестовых пользователей. Эти действия выполняет владелец в Dashboard или авторизованный администратор.

Не помечать пункты выше выполненными на основании этих тестов.

## Откат и восстановление

До слияния production остаётся на `main`; закрытие PR не меняет сайт или IndexedDB пользователя.

После установки новой версии безопасный оперативный откат — **отключить Supabase конфигурацию и пересобрать текущую версию**, сохранив Dexie v3. Это останавливает облако и оставляет все данные доступными локально. Таблицы Supabase не удалять, журналы не чистить. Позже подключить тот же проект/аккаунт и повторить синхронизацию.

Нельзя просто опубликовать старый `b37be9f` поверх уже открытой v3-базы: старый Dexie знает только v2 и откажется открывать более новую версию. Для возврата старого интерфейса нужен совместимый hotfix схемы v3; безопаснее использовать старый checkout в отдельном профиле браузера. Никогда не устранять VersionError через удаление IndexedDB.

Восстановление полного JSON объединяет журнал с текущим без удаления и идемпотентно. Перед восстановлением UI скачивает текущий backup. Копия не содержит auth tokens, binding, sync cursors или receipts, поэтому перенос на новое устройство требует нового подтверждённого входа. Сохраняйте все резервные копии и старую папку OneDrive до проверки живой синхронизации.
