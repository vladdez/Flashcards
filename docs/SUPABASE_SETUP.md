# Подключение Supabase через SQL Editor

Проект: **`lwcmazbqwbhfumjbbzcj`**. Приложение: **https://vladdez.github.io/Flashcards/**.

Это первоначальная установка облачной базы. Пользовательских данных в прежнем OneDrive нет; перенос и экспорт оттуда не нужны. Схема SQL и интеграция уже находятся в репозитории. До настройки сервера доступны локальное обучение, IndexedDB и офлайн PWA.

## 1. Создать таблицы и функции

1. Откройте [SQL Editor нужного проекта](https://supabase.com/dashboard/project/lwcmazbqwbhfumjbbzcj/sql/new), войдите в свой аккаунт Supabase.
2. Создайте новый запрос. Скопируйте **весь** файл [202610130001_supabase_sync.sql](../supabase/migrations/202610130001_supabase_sync.sql), от `begin;` до `commit;`, в редактор.
3. Запустите **Run** с административной ролью `postgres`. Ожидается успешное выполнение без строк результата. Создаются только объекты `public.flashcards_*`: пять таблиц с RLS, шесть представлений и четыре функции. Пользовательские аккаунты и карточки не создаются.
4. В новом запросе выполните **весь** [verify_installation.sql](../supabase/verify_installation.sql). Ожидается одна строка, начинающаяся с `OK: Flashcards schema, RLS, views and grants are installed.` Проверка ничего не записывает и допускает повторный запуск.

Основную миграцию запускают **один раз**. Если она сообщает, что объект уже существует, сначала запустите проверку установки: возможно, схема уже применена. При иной ошибке сохраните её текст; не удаляйте таблицы и не отключайте RLS для обхода ошибки.

Проверка установки проверяет наличие объектов, включение RLS, набор политик, права, режим представлений и функции. Это диагностика конфигурации, а не замена проверке изоляции двух реальных аккаунтов и доставки писем.

## 2. Проверить Data API

В настройках **Data API** оставьте API включённым, а `public` — среди exposed schemas. Дополнительные grants вручную выдавать не нужно: миграция открывает чтение только своему пользователю и запись через проверяемые RPC. Клиент использует `flashcards_head`, `flashcards_pull` и `flashcards_push`.

Если сразу после установки приложение сообщает, что функция не найдена, подождите обновления schema cache. При необходимости выполните отдельно:

```sql
notify pgrst, 'reload schema';
```

## 3. Настроить вход по email

В **Authentication → Sign In / Providers → Email** включите email-вход и разрешите регистрацию новых пользователей. Приложение использует письмо со ссылкой или одноразовым кодом, пароль не требуется.

В [Authentication → URL Configuration](https://supabase.com/dashboard/project/lwcmazbqwbhfumjbbzcj/auth/url-configuration) установите **Site URL**:

```text
https://vladdez.github.io/Flashcards/
```

В **Redirect URLs** добавьте отдельными записями:

```text
https://vladdez.github.io/Flashcards/
http://localhost:5173/
http://127.0.0.1:5173/
http://localhost:5173/Flashcards/
http://127.0.0.1:5173/Flashcards/
http://127.0.0.1:4173/Flashcards/
```

В **Authentication → Email Templates → Magic Link** сохраните шаблон:

```html
<h2>Вход в Flashcards</h2>
<p><a href="{{ .ConfirmationURL }}">Войти в приложение</a></p>
<p>Или введите одноразовый код в приложении: <strong>{{ .Token }}</strong></p>
```

Ссылка открывает корень приложения и возвращает в настройки. Для PKCE открывайте её в том же браузере, где запросили письмо. Код можно ввести в исходной вкладке приложения. Отдельный серверный `/auth/confirm` для этого приложения не нужен.

**iPhone, установленная PWA или браузер внутри почты:** безопаснее скопировать адрес кнопки из письма и вставить в **Настройки → Ссылка из письма → Войти по ссылке** в том приложении, где находятся карточки. Нажмите и удерживайте кнопку в письме → **Скопировать ссылку / Link kopieren**; не открывайте её. Сессия сохранится в текущем приложении. Поддерживаются стандартные ссылки `ConfirmationURL` проекта; менять шаблон писем для этого способа не нужно. Ссылка проверяется через Supabase Auth, её `redirect_to` не открывается. Вход не отправляет библиотеку до отдельного подтверждения объединения.

Если уже появилась ошибка `PKCE code verifier not found in storage`, закройте окно почтового браузера, откройте Flashcards с главного экрана и запросите **новое письмо**. Ранее открытая ссылка могла быть использована. Запрос письма теперь сохраняется при перезагрузке приложения; одноразовая ссылка и код в localStorage не записываются. Не удаляйте PWA и не очищайте данные браузера: локальные карточки хранятся именно там.

Встроенный отправитель Supabase предназначен для ограниченных тестов и принимает только адреса участников организации проекта. Для остальных адресов настройте **Custom SMTP** в Authentication: адрес отправителя, SMTP host, port, username и password своего почтового провайдера. Эти параметры остаются в Supabase, не в GitHub и не в приложении. Проверяйте доставку реальным письмом; включённый Email provider сам по себе её не гарантирует. [Официальные ограничения SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

## 4. Проверить GitHub Pages

В репозитории уже заданы **Settings → Secrets and variables → Actions → Variables**:

```text
VITE_SUPABASE_URL=https://lwcmazbqwbhfumjbbzcj.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
```

Повторно создавать их не нужно. После изменения этих значений потребуется сборка из `main` через workflow **Check and deploy Flashcards**. Применение SQL и настройка Auth не требуют новой сборки. Старые `VITE_MS_*` переменные приложению не нужны.

Workflow сохраняет base `/Flashcards/`, выполняет все проверки и публикует только `main`. PR проверяется без замены работающего сайта. Публичный publishable key допустим в сборке; секретные ключи и пароль базы в frontend не используются.

## 5. Проверить на двух устройствах

1. Откройте приложение, создайте новую тестовую папку, колоду с режимом «Оба направления» и карточку. Оцените её в обоих направлениях.
2. В настройках запросите письмо на свой email. На iPhone скопируйте адрес кнопки входа из письма в **Ссылка из письма** и нажмите **Войти по ссылке**. Если в письме есть цифровой код, можно войти по коду. Выберите **Сравнить и объединить данные**, проверьте аккаунт, подтвердите подключение. Кнопка JSON-копии полезна для будущих библиотек и не является переносом из OneDrive. Дождитесь **Синхронизировано**.
3. На втором устройстве или в отдельном профиле браузера войдите с тем же email и подтвердите подключение. Проверьте папку, колоду, карточку, оба расписания и количество событий.
4. Отключите сеть на обоих устройствах. Измените перевод одной карточки по-разному и запишите ответы на обоих устройствах. Верните сеть: обе версии текста должны появиться в выборе конфликта, оба ответа сохраниться. Разрешите конфликт и дождитесь одинакового результата на устройствах.
5. Перезагрузите приложение: сессия и синхронизация должны восстановиться. Выйдите: локальные данные остаются, новые изменения больше не отправляются.
6. В отдельном чистом профиле войдите с **другим** email: чужие карточки не появляются. SQL/RLS-тесты в репозитории дополнительно проверяют подстановку чужого owner и чужих ссылок; проверка с реальными JWT остаётся отдельной проверкой размещённого сервера.

Без доступа к панели/учётным записям эти шаги не считаются выполненными. Локальные тесты используют PostgreSQL через PGlite и перехват HTTP, а не реальную почту и размещённый Auth.
